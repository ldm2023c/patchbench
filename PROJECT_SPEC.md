# PatchBench Project Specification

## 1. Project Overview

**Project Name:** PatchBench

**Positioning:** Coding Agent Reliability & Failure Analysis Platform

**One-line Description:**

> A reproducible experimentation platform for evaluating, diagnosing and improving coding-agent reliability on real software repositories.

PatchBench is not primarily a leaderboard for comparing coding agents.

Its goal is to study and engineer around a more practical reliability problem:

> Why can the same coding agent succeed on the same task in one run and fail in another, where do failures occur, and whether changes to prompts, models, context, or execution environments produce real and reproducible improvements.

---

## 2. Core Problem

A single successful coding-agent run does not establish reliability.

For a repository-level coding task, an agent may:

- succeed in some runs and fail in others;
- inspect different files across runs;
- identify different root causes;
- produce incomplete or regressive patches;
- spend very different amounts of time or tokens;
- fail because of the environment rather than reasoning.

The core experimental unit is:

> Task × Agent Configuration × Repeated Runs

---

## 3. Project Goals

PatchBench should eventually support the following workflow:

1. Define a reproducible repository-level coding task.
2. Restore the repository to a known base commit.
3. Execute a coding agent in an isolated execution environment.
4. Capture the agent trajectory and generated patch.
5. Automatically evaluate the resulting repository.
6. Persist all artifacts and metadata from the run.
7. Repeat the same experiment multiple times.
8. Aggregate pass rate, duration, stability, and other metrics.
9. Replay and analyze failed runs.
10. Compare controlled changes such as prompt, model, or context strategy.

---

## 4. Core Concepts

### 4.1 Task

A Task describes what problem must be solved.

A Task contains:

- unique task ID;
- repository source;
- base commit;
- task prompt;
- evaluation command;
- timeout configuration;
- optional metadata.

A Task must not contain a specific agent implementation.

### 4.2 Experiment

An Experiment describes how a task is evaluated.

An Experiment combines:

- one Task;
- one Agent configuration;
- N repeated Runs;
- execution configuration;
- experiment metadata.

### 4.3 Run

A Run is one concrete execution of an Experiment.

Every Run must have a unique identifier and its own artifacts.

At minimum, a completed Run should eventually persist:

```text
metadata.json
agent.log
test.log
patch.diff
```

### 4.4 Artifact

Artifacts are files generated by an individual Run.

Examples include:

- agent logs;
- generated patches;
- evaluator logs;
- metadata;
- future trajectory files.

Artifacts must be stored independently for every Run.

---

## 5. MVP v0.1 Scope

PatchBench v0.1 must implement:

- Task specification;
- task configuration validation;
- Git repository reset to a known base commit;
- Docker-based isolated execution;
- one coding-agent adapter: Codex;
- automatic test execution;
- patch capture;
- run metadata collection;
- repeat experiments;
- pass-rate calculation;
- duration measurement;
- filesystem-based result persistence.

The target command is conceptually:

```bash
patchbench experiment \
    --task <task-id> \
    --agent codex \
    --repeat <N>
```

Example output:

```text
Experiment: 20260904-001
Task:        cache_bug_001
Agent:       codex

Runs:        5
Passed:      3
Failed:      2
Pass Rate:   60.0%
Avg Duration: 84.3s
```

---

## 6. Reproducibility Requirements

Every repeated Run should begin from an equivalent state.

At minimum:

- the same repository base commit;
- a clean working tree;
- the same Task specification;
- the same execution image/configuration;
- an independent workspace for every Run;
- immutable persisted artifacts after completion.

PatchBench should explicitly record enough information to reconstruct a Run.

---

## 7. Initial Task Format

The initial task configuration format is YAML.

Conceptual example:

```yaml
schema_version: 1

id: example_bug

repository:
  type: local
  path: fixtures/example_repo
  base_commit: "<git-commit>"

task:
  prompt: |
    Fix the bug described in the repository.

evaluation:
  command: "pytest -q"
  timeout_seconds: 120

metadata:
  language: python
```

The exact schema may evolve, but schema changes should remain explicit and versioned.

---

## 8. Initial Metrics

Required MVP metrics:

- run status;
- pass / fail;
- total duration;
- experiment run count;
- experiment pass count;
- experiment pass rate;
- average run duration.

Optional metrics, when reliably exposed by the agent:

- token usage;
- model name;
- agent step count.

Optional metrics must not block MVP completion.

---

## 9. Failure Analysis Direction

Failure analysis is a core differentiator of PatchBench, but it is not required in the first implementation milestone.

The initial taxonomy may include:

```text
Environment
├── dependency_error
├── timeout
└── agent_crash

Understanding
├── wrong_file
├── missing_context
└── wrong_root_cause

Implementation
├── incomplete_fix
├── wrong_api
└── syntax_error

Evaluation
├── test_failure
└── regression
```

Early failure classification may be performed manually.

Automated LLM-based classification should only be added after a useful manually validated taxonomy exists.

---

## 10. Explicit Non-goals for MVP

The following are explicitly outside PatchBench v0.1:

- Kubernetes;
- distributed execution clusters;
- Firecracker or custom microVM implementation;
- custom container runtime;
- complicated frontend;
- supporting many coding agents;
- large-scale SWE-bench integration;
- automatic LLM failure classification;
- repository-aware context engine;
- RAG system;
- advanced model routing;
- production multi-tenant security.

The MVP should remain local, small, inspectable, and reproducible.

## 11. Future Directions

### V1.5 — Failure Analysis & Replay

Potential additions:

- failure taxonomy;
- failure replay;
- trajectory inspection;
- comparison of successful and failed runs;
- controlled prompt/model experiments.

### V2 — Repository-aware Context Engine

Potential techniques:

- AST analysis;
- symbol dependency graph;
- import/call graph;
- git history;
- context ranking.

The effectiveness of context optimization must be evaluated using downstream coding-agent success rather than subjective demonstrations.

### V3 — Service Architecture

Potential additions:

- FastAPI;
- PostgreSQL;
- Redis;
- worker queue;
- simple dashboard;
- OpenTelemetry.

These are not required until the local experiment engine is stable.

---

## 12. Engineering Principles

PatchBench follows several strict engineering principles:

1. **CLI first.**  
   The core system must work without a web frontend.

2. **Reproducibility before scale.**  
   Five trustworthy runs are more valuable than five hundred uncontrolled runs.

3. **Explicit interfaces.**  
   Agent, sandbox, evaluator, repository, and artifact-storage implementations should be replaceable.

4. **Artifacts before dashboards.**  
   Raw evidence must always be preserved.

5. **Small milestones.**  
   Every milestone must have executable acceptance criteria.

6. **No fabricated metrics.**  
   Resume and project claims must use real measured results.

7. **AI-generated code must remain explainable.**  
   Implementation may be heavily assisted by coding agents, but architecture and engineering decisions must remain understandable and defensible by the project owner.

---

## 13. Definition of MVP Success

PatchBench v0.1 is considered successful when the following command can execute reliably:

```bash
patchbench experiment \
    --task bug_001 \
    --agent codex \
    --repeat 5
```

and produces:

- five independent Runs;
- the same initial repository state for every Run;
- isolated agent execution;
- automatic evaluation;
- PASS/FAIL for every Run;
- aggregate Pass Rate;
- average duration;
- persistent per-run artifacts containing at least:

```text
metadata.json
agent.log
test.log
patch.diff
```

Anything beyond this is an optimization or future feature rather than a requirement for MVP completion.
